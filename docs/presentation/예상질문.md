## 반드시 준비할 것 (7문항)

*답이 막히면 프로젝트 전체가 흔들려 보이는 질문들입니다. 문장을 미리 정해두세요.*

### Q. AI 서비스라면서 실제 LLM이 아니라 Mock 아닌가요? ⚠️

**지금 보시는 배포본은 실제 LLM입니다** — OpenAI `gpt-4o-mini`를 씁니다. 아무 문장이나 입력해보셔도 동작합니다.

저장소 `main`에는 **재현 가능한 Mock Adapter**가 함께 있습니다. 발표·평가 때 매번 같은 결과가 나와야 하고, API 키 없이도 전체 흐름이 돌아가야 해서 남겨둔 경로입니다.

**그래서 둘을 오갈 수 있다는 게 핵심입니다.** 분석기를 `WorkflowAnalyzer` 계약 뒤에 두고 `AI_PROVIDER` 환경 변수 하나로 `mock`과 `llm`을 바꿉니다. Adapter를 갈아 끼워도 REST 계약·상태 전이·DB·프론트 코드는 **한 줄도 바뀌지 않았습니다.** 설계가 실제로 검증된 셈입니다.

> 근거 — application.properties `reqbridge.ai.provider=${AI_PROVIDER:mock}` · OpenAiWorkflowAnalyzer.java · MockWorkflowAnalyzer.java · README 04. AI-Ready by Design

### Q. LLM이 이상한 걸 뱉으면 데이터가 깨지지 않나요? ⚠️

막아뒀습니다. OpenAI 호출은 **JSON Mode**로 스키마를 강제하고, 돌아온 결과는 `AnalyzerOutputValidator`를 **통과한 뒤에만** 업무 데이터가 됩니다 — 순번이 1 미만이거나 중복이면, 원문이 비었으면, 요구사항이 하나도 없으면 거기서 막힙니다.

막히면 작업이 `FAILED`로 떨어지고 `AI_OUTPUT_INVALID`가 기록됩니다. **DB에는 아무것도 안 들어갑니다.** 화면에는 실패 배너와 재시도 버튼이 뜹니다.

그리고 **AI는 DB 식별자·승인 여부·버전 증가를 결정하지 않습니다.** 요구사항 문장·불명확성 분류·질문 문구·충분성 판정·수정안 텍스트만 제안하고 나머지는 백엔드가 정합니다.

> 근거 — AnalyzerOutputValidator.java · OpenAiWorkflowAnalyzer.java(JSON Mode) · prompt-contract.md §2 공통 원칙

### Q. 배포본은 LLM인데 저장소 main은 Mock이네요? 왜 다른가요? ⚠️

같은 코드에서 **환경 변수로 갈리는 것**입니다. `AI_PROVIDER`가 기본값 `mock`이고, 배포 환경에만 `llm`과 API 키를 넣었습니다. 키를 저장소에 두지 않으려는 것이기도 합니다.

LLM Adapter는 별도 브랜치에서 마감 직전까지 다듬고 있어 `main` 머지가 아직입니다. **다만 배포본이 그 브랜치로 돌고 있으니 동작은 확인된 상태입니다.** 지금 화면에서 바로 확인하실 수 있습니다.

> 근거 — application.properties · feat/ai-connect 브랜치 · 배포 API 실측 응답

### Q. 그러면 AI가 요구사항을 확정하는 건가요? ⚠️

아니요. **확정은 사람만 합니다.** 모든 문제가 해결돼도 시스템은 수정안을 `PROPOSED`로 제안할 뿐이고, 담당자가 승인해야 `CONFIRMED`가 됩니다. 자동 승인 경로는 아예 만들지 않았습니다.

거절도 남습니다 — 거절 사유와 거절된 수정안이 이력으로 보존되고, 원문은 어떤 경우에도 덮어쓰지 않습니다.

> 근거 — API Spec §4.1 상태 전이표 · Runbook §12 핵심 4 "최종 결정은 사람"

### Q. 고객 계정이 없는데 고객이 어떻게 답변하나요? ⚠️

이번 범위에서는 **PM이 대리 입력**합니다. 고객에게는 「고객 질문서」 Preview를 전달해 답을 받고, PM이 화면에 옮겨 적는 구조입니다.

로그인·권한은 명세에서 **의도적으로 제외**했습니다. 이번 프로젝트의 초점이 「요구사항이 확정되기까지의 흐름」이라, 계정 체계를 넣으면 그 흐름을 검증할 시간이 줄어든다고 판단했습니다. 로드맵에 고객 계정 직접 협업이 들어 있습니다.

> 근거 — docs/usecase-diagram.md UC-04 "고객 답변 대리 입력" · README 06. Scope · API Spec §10 "로그인 도입을 범위에 추가하지 않는다"

### Q. 확정된 요구사항을 개발팀에 어떻게 넘기나요? 다운로드가 없는데요. ⚠️

「개발팀용 Preview」 화면으로 넘깁니다. 확정본과 **그 문장이 어떤 고객 답변을 근거로 만들어졌는지**를 함께 보여줍니다 — 원문, 승인된 수정안, 근거 답변, 버전이 한 화면에 있습니다.

파일 다운로드는 이번 범위에서 **명시적으로 제외**했습니다. 로드맵의 PDF·Word·CSV 내보내기가 그 자리입니다.

> 근거 — API Spec §5.18 · README 06. Scope ROADMAP · 명세 §10 "다운로드를 구현 범위에 추가하지 않는다"

### Q. 불명확성이 없는 요구사항은 영영 확정을 못 하나요? ⚠️

아닙니다. **원문 직접 승인** API가 있습니다 — `POST /api/requirements/{id}/confirm`. 열린 문제가 없는 요구사항을 질문·답변 없이 바로 확정합니다.

이건 시연 준비 중에 **프론트가 발견해 백엔드에 요청서로 올린 항목**입니다. 프론트에서 임의로 확정 상태를 만들지 않고 API를 기다렸습니다.

> 근거 — docs/frontend/requests/백엔드-추가-요청사항.md · RevisionController.java:61 · usecase UC-08

## 자주 나올 질문 (7문항)

*제품과 시연 흐름에 대한 일반적인 물음입니다.*

### Q. 한 문장으로 뭘 하는 서비스인가요?

고객이 준 **읽을 수는 있지만 개발할 수는 없는 요구사항**을, 질문과 답변을 거쳐 **측정 가능한 기준**으로 바꿔주는 도구입니다.

예를 들어 "많은 사용자의 요청에 빠르게 응답해야 한다"는 문장은 그대로는 구현도 테스트도 못 합니다. ReqBridge는 여기서 「최대 동시 사용자 수」와 「목표 응답 시간」이 빠졌다는 걸 찾아내 고객에게 물을 질문을 만듭니다.

> 근거 — README 01. Why ReqBridge · Runbook §2 PER-002

### Q. 기존에 요구사항 관리 도구는 많은데 뭐가 다른가요?

기존 도구는 대부분 **이미 정리된 요구사항을 담는** 그릇입니다. ReqBridge는 그 앞 단계 — **정리되기 전의 문장을 정리하는 과정** 자체를 다룹니다.

그리고 분석 한 번으로 끝내지 않습니다. 문서 분석 → 질문 → 답변 → **재판정** → 수정안 → 검토 → 확정이 하나의 흐름으로 이어지고, 답변이 부족하면 같은 문제에 다음 회차 질문이 생깁니다.

> 근거 — README 02. Core Experience · Runbook §12 핵심 1

### Q. 고객이 애매하게 답하면 어떻게 되나요?

저장만 하고 끝내지 않고 **그 답변이 실제로 문제를 해결했는지 다시 판정**합니다. 시연에서 일부러 "많이 접속할 것 같습니다"라고 답해 이 분기를 보여드립니다.

불충분하면 원래 질문은 `ANSWERED`로 남고 문제는 `OPEN`인 채로, **같은 문제에 2회차 질문**이 새로 열립니다. 충분한 답변만 `RESOLVED`가 됩니다.

> 근거 — Runbook Step 6~8 · API Spec §4 "불충분한 답변의 질문은 ANSWERED로 남고…"

### Q. 불명확성 7종은 어떤 기준으로 나눈 건가요?

개발자가 **구현하거나 테스트할 때 막히는 지점** 기준입니다 — 수량, 성능, 조건, 주체, 성공 기준, 용어, 예외 처리.

이 문자열은 DB·Java·API·프론트가 **대소문자까지 정확히 일치**시킵니다. 임의 보정이나 fallback 라벨을 금지해서, 계약이 어긋나면 조용히 묻히지 않고 드러나게 했습니다.

> 근거 — prompt-contract.md §2-3 · API Spec §4.1 "대소문자 보정·ordinal·임의 fallback을 허용하지 않는다"

### Q. PDF는 어떻게 처리하나요?

서버가 PDF에서 **텍스트를 추출해 Document로 저장**하고, 분석에는 그 텍스트를 씁니다. PDF 바이너리를 분석기에 넘기지 않습니다. 원본 파일은 Supabase Private Storage에 따로 보관합니다.

업로드하면 제목이 비어 있을 때만 파일명으로 자동 채우고, 업로드와 분석이 **한 번의 동작**으로 이어집니다.

> 근거 — Runbook Step 2 · docs/frontend/requests/프론트엔드-추가-요청사항.md §3.3

### Q. 배포는 어디에 되어 있나요?

프론트는 **Vercel**, 백엔드는 **Railway**, DB는 **Supabase PostgreSQL**입니다. Vercel이 `/api/*`를 Railway로 넘기도록 rewrite를 걸어두어 브라우저에서는 같은 출처로 보입니다.

프론트는 백엔드 없이도 돌아가는 **Mock 모드**를 따로 갖고 있습니다. 화면 개발과 시연이 백엔드 상태에 묶이지 않게 하려고 분리했습니다.

> 근거 — frontend/vercel.json · package.json `dev:mock` / `build:mock`

### Q. 역할은 어떻게 나눴나요?

PM/기획, 프론트 2명, 백엔드 2명입니다. 프론트는 화면 단위로 갈랐습니다 — **문서·분석·요구사항 목록**과 **요구사항 검토 Workflow·Preview**. 공통 계층(라우터·API client·공통 컴포넌트·enum)은 합의 문서로 인터페이스를 먼저 고정하고 병렬로 작업했습니다.

경계에서 부딪히는 항목은 문서로 주고받았습니다 — 반영 현황서, 요청서, 회신. PR도 각자 올려 기여가 섞이지 않게 했습니다.

> 근거 — README 07. Team · docs/frontend/FE_Check_B_반영_현황.md · FE_Check_C_반영_현황.md

## 깊게 파고들 때 (7문항)

*설계를 캐물을 때 나오는 질문입니다. 여기서 답이 나오면 신뢰도가 크게 올라갑니다.*

### Q. 두 사람이 같은 요구사항을 동시에 고치면 어떻게 되나요? 🔎

두 겹으로 막습니다. 첫째, 한 요구사항에 **진행 중인 작업이 있으면** 새 답변·검토·재생성 요청이 `409 ANALYSIS_IN_PROGRESS`로 막히고 화면도 입력을 잠급니다.

둘째, 모든 변경 요청은 `expectedContentVersion`을 함께 보냅니다. 그사이 내용이 바뀌었으면 `409 CONTENT_VERSION_CONFLICT`가 나고, 화면은 최신 상태를 다시 불러오되 **사용자가 입력하던 내용은 지우지 않습니다.**

> 근거 — API Spec §6.2 검증 순서 · §6.3 기능별 규칙 · §8 activeAnalysis 잠금

### Q. 그 버전 숫자는 프론트가 계산하나요? 🔎

아니요. **프론트는 +1 하지 않습니다.** 출처가 세 곳뿐입니다 — workflow 조회 응답, 답변 응답의 `contentVersion`, 검토 응답의 `requirement.contentVersion`. 마지막 서버 응답값을 그대로 되돌려줍니다.

재생성 응답만 예외인데, 그건 응답이 Analysis라 버전이 없습니다. 그래서 polling이 끝난 뒤 workflow를 다시 조회해 받습니다. **이 규칙 하나로 409의 절반이 사라집니다.**

> 근거 — FE 합의 v0.2 §7 · docs/frontend/fe-c-work-notes.md · API Spec §8

### Q. 거절하면 왜 버전이 오르나요? 🔎

거절 사유 자체가 **새로운 입력**이기 때문입니다. 다음 수정안은 기존 답변에 거절 사유까지 반영해 만들어지므로, 입력이 달라진 겁니다.

승인은 반대로 버전을 유지합니다 — 내용이 바뀐 게 아니라 확정된 것이니까요. 그리고 거절된 수정안의 `inputContentVersion`은 **만들어질 당시 값을 그대로 유지**합니다. 나중에 봤을 때 "이 수정안은 어느 시점 입력으로 만들어졌나"를 알 수 있어야 하기 때문입니다.

> 근거 — API Spec §4.1 상태 전이표 · §6.3 · Runbook Step 12

### Q. 분석 도중에 새로고침하면요? 🔎

복구됩니다. 화면이 뜰 때 **문서의 분석 이력을 조회해 진행 중인 작업을 찾고** polling을 이어받습니다. 잠금 상태도 같이 복구돼서, 중복 제출이 생기지 않습니다.

그리고 **분석 실패는 HTTP 오류가 아닙니다.** 200으로 오되 `status=FAILED`와 실패 코드가 담깁니다. 그래서 네트워크 오류 배너와 작업 실패 배너를 **다른 컴포넌트로 분리**했습니다.

> 근거 — API Spec §6.1 · §8 "새로고침 시 PENDING/PROCESSING을 찾아 polling을 재개한다"

### Q. 같은 요청을 두 번 보내면 중복 처리되나요? 🔎

아닙니다. **같은 답변·같은 결정의 재전송은 저장된 결과를 그대로 돌려줍니다.** 버전이 추가로 오르지 않고 부수 효과도 없습니다. 진행 중이면 202, 끝났으면 200입니다.

반대로 **다른 내용으로 덮어쓰려는 시도는 막습니다** — 이미 답한 질문에 다른 답변은 `409 ANSWER_ALREADY_SUBMITTED`, 검토 결정을 바꾸려 하면 `409 REVISION_ALREADY_REVIEWED`입니다.

> 근거 — API Spec §6.3 기능별 규칙

### Q. Supabase 연결에서 특별히 신경 쓴 게 있나요? 🔎

네. Supabase가 제공하는 **Transaction pooler(6543)를 쓰지 않고 Session pooler(5432)**를 씁니다. Hibernate가 prepared statement를 쓰는데 Transaction 모드는 이를 지원하지 않아, 붙이면 런타임에 오류가 납니다.

그리고 Supabase 프로필에서는 **Flyway를 끄고 Hibernate는 `validate`만** 돌립니다. 애플리케이션이 운영 스키마를 마음대로 바꾸지 못하게 하려는 것입니다.

> 근거 — docs/backend/supabase-connection.md §2 · docs/backend/core-notes.md 스키마 결정

### Q. 데이터 정합성은 애플리케이션에서만 지키나요? 🔎

아니요, **DB 제약으로도 보호**합니다. 한 문서/요구사항의 활성 작업 중복, 번호 중복, 한 요구사항에 `PROPOSED` 수정안이 둘 이상 생기는 것을 DB가 막습니다.

복합 FK로 **요구사항과 최초 분석의 문서가 같도록**, **질문과 문제의 요구사항이 같도록** 강제했습니다. 애플리케이션 코드가 틀려도 잘못된 조합이 저장되지 않습니다.

## 시연 중 사고 대비 (3문항)

*화면 앞에서 벌어질 수 있는 일과, 그때 할 말입니다.*

### Q. 답변을 입력했는데 화면이 멈춘 것처럼 보입니다

분석 작업이 도는 동안 **의도적으로 잠그는 상태**입니다. 상단에 "분석 처리 중"이 뜨고 입력·검토 버튼이 비활성됩니다. 1초 간격으로 상태를 조회하다가 끝나면 자동으로 풀립니다.

시연에서 이 순간이 오면 그냥 설명하시면 됩니다 — **"같은 요구사항에 작업이 두 개 겹치지 않도록 막는 구간입니다."**

> 근거 — API Spec §6.1 polling 규칙 · §8

### Q. 분석이 실패하면 시연이 끊기나요?

아니요. 실패 배너와 **재시도 버튼**이 나옵니다. 재시도는 같은 입력·같은 버전으로 새 작업을 만들고 원래 작업과 연결해 기록합니다.

이미 재시도한 작업에 또 요청해도 **형제 작업이 늘어나지 않고** 기존 재시도를 돌려줍니다.

> 근거 — API Spec §6.3 · 프론트 AnalysisFailureBanner

### Q. 시연용 답변을 정확히 뭐라고 입력해야 하나요?

**배포본(LLM)에서는 아무 문장이나 됩니다.** 숫자가 없으면 불충분으로 보고 다시 묻고, 정량 기준이 있으면 해결로 넘어갑니다. 즉석에서 심사위원이 불러주는 답을 넣어도 동작합니다 — 오히려 이게 좋은 시연 포인트입니다.

**Mock 모드로 시연한다면 문장이 정확해야 합니다.** 지정된 세 문장 외에는 작업이 실패합니다.

> 근거 — Runbook Step 6·8·10·12 · MockWorkflowAnalyzer.assessAnswer (지정 문장 외 AiOutputInvalidException)
