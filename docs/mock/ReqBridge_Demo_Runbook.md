# ReqBridge Demo Runbook

## 1. 데모 목적

본 데모는 고객 요구사항 문서를 업로드한 뒤 ReqBridge가 다음 흐름을 어떻게 지원하는지 보여주는 것을 목적으로 합니다.

PDF 업로드  
→ 요구사항 분석  
→ 불명확성 식별  
→ 고객 질문 생성  
→ 답변 입력  
→ 답변 재판정  
→ 수정안 생성  
→ 수정안 거절 및 재생성  
→ 최종 승인  
→ 확정 요구사항 Preview

이번 데모에서 AI 판단은 실제 LLM이 아니라 Mock Adapter를 사용합니다.

웹 서비스의 Workflow, 상태 전이, 질문/답변, 수정안, 승인/거절, DB 저장은 실제로 동작하며, AI 판단 부분만 미리 준비한 Mock 시나리오를 사용합니다.

---

## 2. 데모 준비물

### 시연용 요구사항 문서

`rfp_demo_requirement.pdf`

문서 내 핵심 시연 요구사항:

**PER-002 — 대용량 상품 조회 성능 보장**

초기 요구사항:

시스템은 많은 사용자의 동시 상품 조회 요청에 빠르게 응답해야 한다.  
부하 시험은 10분 동안 수행하며 성공 응답 비율은 99.9% 이상이어야 한다.

이 요구사항에는 다음 정보가 명확하지 않습니다.

- 최대 동시 사용자 수
- 목표 응답 시간
- 응답 시간 측정 지표

이를 중심으로 질문 → 답변 → 수정안 생성 흐름을 시연합니다.

# 3. 메인 데모 시나리오

## Step 1. 프로젝트 생성

### 발표자 동작

새 프로젝트를 생성합니다.

예시 프로젝트명:

`바이오 원재료 이력관리 플랫폼`

### 발표 멘트

"고객에게 전달받은 요구사항 문서를 프로젝트 단위로 관리할 수 있습니다."

### 확인

프로젝트가 정상적으로 생성되고 프로젝트 상세 또는 문서 등록 화면으로 이동하는지 확인합니다.

## Step 2. PDF 요구사항 문서 업로드

### 발표자 동작

다음 파일을 업로드합니다.

`rfp_demo_requirement(1).pdf`

### 발표 멘트

"기존에는 요구사항을 직접 텍스트로 입력할 수도 있고, 실제 고객에게 받은 PDF 문서를 그대로 업로드할 수도 있습니다."

### 확인

- PDF 업로드 성공
- 문서 제목 표시
- `sourceType = FILE`
- PDF에서 추출된 텍스트가 Document로 등록됨

### 주의

PDF 원본은 Supabase Storage에 저장되고, 분석에는 PDF binary가 아니라 서버에서 추출한 `Document.content`가 사용됩니다.

# 12. 발표 중 강조할 핵심 포인트

## 핵심 1. 단순 분석 서비스가 아님

문서 분석  
→ 질문  
→ 답변  
→ 재질문  
→ 수정안  
→ 검토  
→ 확정

까지 하나의 Workflow로 연결됩니다.

## 핵심 2. 고객 답변을 무조건 신뢰하지 않음

`많이 접속할 것 같습니다.`

같은 답변은 저장만 하고 끝내지 않고, 실제로 문제를 해결했는지 재판정합니다.

## 핵심 3. 원문을 임의로 덮어쓰지 않음

- 원래 Requirement 유지
- 질문/답변 이력 유지
- Revision 이력 유지
- 거절 이력 유지
- 최종 승인본 별도 관리

## 핵심 4. 최종 결정은 사람

Mock/AI는 제안만 합니다.

최종:

- `REJECT`
- `APPROVE`

는 PM이 수행합니다.

## 핵심 5. 실제 AI가 아니어도 서비스 Workflow는 동작

현재 데모에서는 AI 판단을 Mock Adapter로 처리합니다.

추후 실제 AI Adapter를 연결해도 Workflow/API 구조는 그대로 사용할 수 있도록 구성합니다.
