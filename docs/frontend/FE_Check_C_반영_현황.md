## 3. B의 6절 메모에 대한 회신

### 3.1 PrimeVue — 넣었습니다

PDF 업로드에 `FileUpload`를 씁니다. 기본 `<input type="file">`은 OS마다 다른 모양으로 그려져 같은 화면의 다른 단추들과 아무 관계 없어 보였습니다.

넣으면서 정한 것:

- **v4 계열로 고정합니다.** v5는 테마가 유료 라이선스라 화면 오른쪽 아래에 `Invalid PrimeUI License` 배지가 뜹니다. `primevue@4` + `@primevue/themes@4`
- `cssLayer`로 PrimeVue 규칙을 layer 안에 가둡니다. layer 밖 규칙이 항상 이기므로 `style.css`의 토큰이 PrimeVue 기본값에 밀리지 않습니다
- `darkModeSelector`를 쓰지 않는 선택자로 묶습니다. 기본값 `system`이면 OS가 다크 모드일 때 PrimeVue만 혼자 어두워집니다
- 위젯이 들고 오는 에메랄드색은 이 화면에서 「해결·완료」를 뜻하는 색이라, 아직 아무 일도 안 한 단추가 그 색이면 뜻이 어긋납니다. 조용한 단추와 같은 결로 낮췄습니다
- 위젯이 파일명 자리에 영어로 `No file chosen`을 박아 둡니다. 그 자리는 감추고, 이름과 크기는 바로 아래 줄에서 우리가 적습니다

`auto=false`라 **고르는 일만 위젯이 맡고 업로드는 아래 단추가 계속 맡습니다.**

### 3.2 `Preview 열기` → `미리보기` — 반영

C가 넣은 링크라 C에서 처리하는 게 자연스럽다고 하셔서 이 브랜치에서 바꿨습니다.

### 3.3 Mock 5-1 — 회신 기다립니다

`extractRequirements`가 B 영역이라 A안(분석 Mock이 1회차 질문을 만들고 `CLARIFYING`으로 전환) 동의 여부를 주시면 C가 PR로 올리겠습니다.

### 3.4 2.2 favicon — 반영

B 문서 4.4에서 「디자인 소유가 없다」고 하신 항목입니다. 투명 배경 심볼을 favicon과 Apple touch icon에 연결했습니다.

## 4. B 화면을 건드린 부분 — 먼저 봐 주세요

**이 문서에서 가장 중요한 절입니다.** `feat/fe-b-ux`의 파일 중 다섯 개를 고쳤습니다.

| 파일 | 무엇을 |
| --- | --- |
| `ProjectListView.vue` | 마크업을 디자인 시스템으로 |
| `DocumentListView.vue` | 마크업을 디자인 시스템으로 + FileUpload |
| `DocumentDetailView.vue` | 마크업을 디자인 시스템으로 + `Preview 열기` 문구 |
| `AppLayout.vue` | 셸 스타일이 이 파일 안에 있어서 |
| `statusLabels.js` | 라벨은 그대로. `STATUS_TONES`만 |

`router/index.js`와 `useBreadcrumbLabels.js`는 **건드리지 않았습니다.**

### 4.1 왜 건드렸나

`feat/fe-b-ux`의 세 화면은 디자인이 들어가기 전 시점에서 갈라져 나왔습니다. 그대로 합치면 다섯 화면 중 둘(workflow · Preview)만 디자인이고 셋은 하드코딩 색(`#2563eb`, `#e5e7eb`)에 페이지 여백도 없는 상태가 됩니다. 실제로 합쳐서 띄워 보니 본문이 창 왼쪽 모서리에 붙었습니다.

화면마다 다른 서비스처럼 보이는 상태로 둘 수 없어서, **동작은 그대로 두고 놓이는 자리만 바꿨습니다.**

### 4.2 그대로 가져온 동작 (판단은 B 것입니다)

- PDF 패널을 직접 입력 **위**로
- 버튼 `PDF 업로드 및 분석` / 진행 중 `업로드 및 분석 중…`
- 업로드 후 `startDocumentAnalysis()` 호출 → 문서 상세로 이동. **실패해도 삼킵니다** — 문서는 이미 저장됐고 상세의 `restoreActiveAnalysis()`가 이력을 복구합니다
- 제목이 비어 있을 때만 파일명으로 자동 입력. 이미 적은 제목은 덮지 않습니다
- `formatFileSize`로 파일명·크기 표시
- `uploading` 동안 제목·파일·버튼 잠금
- `AMBIGUOUS` · `CLARIFYING`을 목록 위로, 같은 그룹은 `sequenceNo` 오름차순
- **`sequenceNo`는 재번호 매기지 않음** — 5번이 위에 와도 문서의 5번째 요구사항입니다
- 액션 문구 `불명확성 확인 →` / `요구사항 보기 →`
- 왼쪽 빨간 강조선 없음
- 직접 입력 폼 빈 값 시작

### 4.3 제가 판단을 바꾼 곳 — 세 군데뿐입니다

1. **`AppLayout`의 이름 fallback을 B 것으로 채택했습니다.** 저는 `String(id)`였고 B는 `'항목'`이었는데, ID를 절대 안 보이게 하는 쪽이 요청서 취지에 맞습니다
2. **`getProject` 실패를 삼킵니다.** B는 `Promise.all`에 묶어 프로젝트명 조회가 실패하면 문서 목록까지 에러 화면이 됩니다. 이름은 못 읽어도 문서 목록은 보여야 해서 `.catch(() => null)`을 걸었습니다
3. **등록 폼의 `sticky`를 뺐습니다.** 폼이 스크롤을 따라오면 목록을 훑는 내내 시야 절반을 차지하고, 폼이 길어지면 그 안에서 또 스크롤이 생깁니다. 원문·조회 기준처럼 「보면서 작업하는 판」만 따라오게 뒀습니다

**되돌리기 쉽습니다.** 세 곳 다 한 줄짜리라, 아니라고 하시면 B 것으로 돌리겠습니다.

## 5. 디자인

> **먼저 밝힙니다.** 이 절은 `FE_Check.md`가 요청한 범위가 아닙니다. 요청서의 디자인
> 항목은 2.2 favicon 하나뿐입니다. 다만 채수아 님이 「디자인은 저는 잘 모르겠습니다,
> 다들 피드백 좀 내주세요」라고 하셨고 B 문서 4.4도 「인계서·명세에 디자인 소유가
> 없다」며 열어 두어, 그 빈자리를 채운 **제안**입니다. 반영 여부는 팀이 정하시면 됩니다.

### 5.1 무엇을 기준으로 했나

채수아 님이 올려주신 화면(`/projects`)의 **계산된 스타일을 실제로 재서** 맞췄습니다.
눈대중이 아니라 값입니다.

```
본문 폭      1360 -> 1200px      좌우 여백  40 -> 24px
기둥 간격    32 -> 20px          카드 안쪽  19 -> 24px
목록 머리말  14/19/13 -> 16/24   행        15/16 -> 18/24/19
카드 모서리  4 -> 8px            헤더 높이  69 -> 60px
```

그 화면이 이 저장소의 디자인 토큰(`--fg-950` `--logo-blue` `--accent-700` `--ease`)을
그대로 쓰고 있어서, **시스템을 버리는 게 아니라 장식만 덜어내면 같은 곳에 도착했습니다.**

### 5.2 덜어낸 것

- **바탕을 흰색으로.** 색 있는 지반 위에서는 카드가 「떠 있는 판」으로 보여 업무 화면치고
  장식이 앞섭니다. 지반과 카드가 같은 색이 되므로 카드의 끝은 테두리가 혼자 맡습니다
- **바탕의 푸른 글로우와 필름 그레인 제거.** 흰색으로 정한 이상 그 위에 색과 잡티를
  얹으면 흰색이 아니게 됩니다
- **상단 히어로에서 디더 파도와 워터마크 글자 제거.** 236px 쓰던 띠가 90px로 줄어
  본문이 그만큼 빨리 나옵니다
- **기둥 사이 세로 구분선 제거.** 흰 바탕에 카드가 테두리로 서고 나니 그 선이 「기둥을
  나누는 규칙」이 아니라 화면을 반으로 접은 자국처럼 읽혔습니다
- **쓰이지 않게 된 그래픽 컴포넌트 8개 삭제.** 서로만 참조하고 화면에서는 아무도
  부르지 않았습니다
- **서체를 넷에서 하나로.** Archivo·SUITE·JetBrains Mono를 걷고 Pretendard만 남깁니다.
  화면 제목이 전부 한글이 된 뒤로 Archivo는 쓰이지 않았고, JetBrains Mono는 한글
  글리프가 없어 라벨과 본문이 폴백하면서 등폭 서체의 넓은 자간만 남았습니다.
  그래서 「원 문」 「1 회 차」처럼 벌어져 업무 화면의 글이 코드처럼 읽혔습니다
- **설명을 위한 상시 문구 제거.** 카드 부제(「원문을 붙여넣어 등록」), 「분석을 시작하면
  요구사항이 추출됩니다」(버튼에 이미 「분석 요청」), 「승인된 수정안의 본문입니다」
  (카드 제목이 「확정본」), 「1초 간격으로 상태를 조회하고 있습니다」(구현 사정).
  안내가 필요한 순간은 데이터가 없을 때뿐이고 그건 EmptyState가 맡습니다

### 5.3 상태를 어떻게 보이게 했나

**알약을 벗겼습니다.** 배지에 바탕과 테두리를 주면 한 줄에 둘만 놓여도 「누를 수 있는
것」이 여럿인 화면처럼 보입니다. 상태는 누르는 것이 아닙니다. 지금은 앞에 7px 점 하나와
색 글자로만 씁니다. 불명확성 유형(「수량 누락」)은 상태가 아니라 분류라 점 없이 글자로
둡니다 — 한 줄에 알약이 둘이면 어느 쪽이 지금 할 일을 말하는지 알 수 없습니다.

색은 **「누가 다음 행동을 하는가」**로 읽습니다.

```
호박 = 사람이 손을 대야 한다   불명확성 발견 · 보완 답변 필요 · 미해결 · 답변 대기
보라 = 사람이 판단해야 한다     수정안 승인 대기 · 제안
무채 = 기다리면 된다            추출 완료 · 대기 · 분석 중 · 답변됨
초록 = 끝났다                   확정 완료 · 해결 · 승인 · 분석 완료
빨강 = 잘못됐다                 실패 · 거절
```

`STATUS_TONES`만 바뀌고 **라벨(4.2)과 tone 이름은 B가 정한 그대로**입니다.

### 5.4 처리 단계를 세로 스텝퍼로

4.2로 상태 이름이 「검토 중」에서 「수정안 승인 대기」로 길어지면서, 272px 참조 기둥에
다섯 이름을 한 줄로 늘어놓을 수 없게 됐습니다. 칸당 몫은 54px인데 가장 긴 이름은
90px을 넘어 서로 겹칩니다.

이름을 줄여 다섯 개를 다 넣는 선택지도 있었지만, 그러면 배지와 여정이 같은 상태를
다른 말로 부르게 되어 사용자가 찾아야 할 단어가 두 벌이 됩니다. **세로로 세우면 이름마다
한 줄을 온전히 씁니다.** 지나온 단계는 번호 대신 체크로 바꿔, 어디까지 왔는지가 두
기호의 경계로 드러납니다.

### 5.5 강조를 자리에 맞게

전체를 키우는 것은 강조가 아닙니다. 다 굵어지면 굵은 것이 화면의 기본값이 되어 정작
세운 자리가 묻힙니다. 무엇을 **먼저 읽어야 하는지**로 단계를 짰습니다.

세운 것 — 질문 문장(이 화면에서 읽고 답해야 하는 단 하나의 문장) · 불명확성 유형
(무엇이 잘못됐는지를 한 낱말로) · 건수(「프로젝트 **1**건」의 1) · 문장 속 수치
(「확인된 불명확성 **2**건」) · 목록 제목(카드 밖 상위 제목인데 그 아래 카드 제목보다
작아 위계가 역전돼 있었습니다).

낮춘 것 — 라벨 굵기와 색, 원문·확정본 같은 읽는 자료, 대제목(42 -> 38px).

목록 카드의 머리말에는 아주 옅은 브랜드색을 깔아 표의 머리 행으로 만들었습니다.
괘선 하나만으로는 머리말과 첫 행이 같은 줄로 읽혔습니다. 폼 카드에는 깔지 않습니다 —
색 있는 머리말은 「아래는 데이터」라는 뜻이고 폼은 입력 자리입니다.

### 5.6 팀 시안과 아직 다른 것

- **폰트 로딩처.** 그쪽과 같은 Pretendard를 쓰지만 CDN 링크 구성이 다를 수 있습니다
- **PrimeVue 버전.** 그쪽은 자체 preset(`./theme`)에 `cssLayer: false`, 이쪽은 Aura
  preset에 `cssLayer` 사용입니다. 합칠 때 한쪽으로 맞춰야 합니다

맞출지 회신 주시면 반영하겠습니다.
