# 프론트엔드 사용성 수정 요청서

## 1. 목적

이번 검토에서는 디자인보다 화면의 큰 정보 구조와 가독성, 사용자가 해야 할 행동의 명확성, 실제 동작 흐름을 우선 확인해 주세요.

현재 핵심 문제는 화면에 개발용 정보가 노출되고, 실제 업무와 맞지 않는 표현이 사용되며, 사용자가 검토할 대상과 다음 행동을 찾기 어렵다는 점입니다.

아래에는 기존 프론트에서 확인된 명확한 문제와 현재 개선본에 반영한 수정 결과만 정리했습니다.

- 확인 링크: [https://tail-jokes-axis-immunology.trycloudflare.com](https://tail-jokes-axis-immunology.trycloudflare.com)

## 2. 공통 수정사항

### 2.1 영문 중심 표현 제거

문제:

- `Projects`, `Documents`, `Document`, `Requirement`, `Preview` 같은 영문 화면명이 실제 기능을 바로 설명하지 못했습니다.
- `Preview 열기`처럼 한글과 영문이 섞인 표현이 사용됐습니다.

수정:

- `Projects` → `프로젝트`
- `Documents` → 현재 프로젝트명
- `Document` → 실제 문서명
- `Requirement` → `요구사항 검토`
- `Preview` → `문서 미리보기`
- `Preview 열기` → `미리보기`

### 2.2 웹페이지 아이콘 변경

문제:

- 브라우저 탭 아이콘에 불필요한 배경이 보여 로고가 정돈되지 않았습니다.

수정:

- 투명 배경의 `reqbridge-mark.png`를 favicon으로 연결했습니다.
- Apple touch icon도 같은 투명 배경 심볼로 변경했습니다.
- 상단바 로고도 동일한 심볼을 사용합니다.

### 2.3 개발용 정보와 잘못된 번호 표기 제거

내부 ID는 DB나 Mock 데이터가 프로젝트, 문서, 요구사항과 질문을 구분하기 위해 사용하는 저장번호입니다. 사용자에게 보여줄 문서 내 순번이나 질문 회차가 아닙니다.

원격 프론트의 Mock 미리보기 화면에서는 같은 요구사항을 다음과 같이 서로 다른 번호로 표시했습니다.

- 카드 상단의 `#1 요구사항`: 문서에서 첫 번째로 추출된 요구사항이라는 뜻입니다.
- 화면 하단의 `요구사항 401 v1`: 같은 요구사항에 Mock이 부여한 내부 ID `401`입니다. 문서의 401번째 요구사항이라는 뜻이 아닙니다.
- `1회차 질문 601`, `1회차 질문 602`: 첫 번째 답변 회차에 포함된 질문의 내부 ID입니다. 601번째·602번째 질문이라는 뜻이 아닙니다.

이 번호들이 별도 설명 없이 사용자용 번호처럼 표시되어, 같은 요구사항이 `1번`인지 `401번`인지 혼동하게 했습니다.

문제:

- 프로젝트 화면에 `API 데이터 원본`과 `MOCK` 같은 개발 확인용 문구가 노출됐습니다.
- 프로젝트와 문서 목록에 DB 저장번호가 표시되어 목록 순번처럼 보였습니다.
- `질문 3`, `수정안 7`처럼 질문 회차나 수정안 차수로 오해할 수 있는 번호가 표시됐습니다.
- 문서 내 요구사항 순번과 DB 저장번호가 모두 `요구사항 N` 형식으로 표시되어 서로 구분되지 않았습니다.

수정:

- `API 데이터 원본`, `MOCK` 표시를 제거했습니다.
- 프로젝트 목록과 문서 목록에서 DB ID를 제거했습니다.
- 프로젝트명, 문서명과 요구사항 코드를 주요 식별 정보로 사용합니다.
- 질문 ID는 `확인 질문`, 승인 근거는 `근거 답변`으로 표시합니다.
- 승인된 수정안 ID 대신 `승인된 수정안`으로 표시합니다.
- 수정안은 내부 ID가 아니라 `1차 수정안`처럼 회차로 표시합니다.
- 요구사항 상세 경로는 ID 대신 `요구사항 검토`로 표시합니다.

남은 항목:

- 현재 수정본의 미리보기 하단 `조회 기준 버전`에는 DB 저장번호가 `요구사항 10`처럼 아직 표시됩니다. 문서의 실제 요구사항 순번으로 바꾸거나 화면에서 제거해야 합니다.

## 3. 프로젝트와 문서 등록

### 3.1 프로젝트 진입 동선이 불명확하던 문제

문제:

- 행을 누르면 어디로 이동하는지 명확하지 않았습니다.
- 프로젝트에 진입한 뒤 하위 화면에서 현재 프로젝트명을 바로 확인하기 어려웠습니다.

수정:

- 프로젝트명을 주요 제목으로 표시합니다.
- 하위 문서 화면에서도 프로젝트명과 설명을 유지합니다.
- 각 프로젝트에 `프로젝트 열기` 액션을 표시합니다.

### 3.2 직접 입력 기본값 제거

문제:

- 새 문서의 제목과 원문 입력란에 데모 값이 기본으로 채워져 있었습니다.
- 예시인지 실제 저장 데이터인지 구분하기 어려웠고, 그대로 등록될 위험이 있었습니다.

수정:

- 제목과 원문은 빈 값으로 시작합니다.
- 입력 방법은 placeholder로만 안내합니다.

### 3.3 PDF 등록 흐름 수정

문제:

- 시연의 시작점인 PDF 업로드보다 직접 입력이 먼저 보였습니다.
- 파일 선택 버튼이 브라우저 기본 UI로 표시됐습니다.
- 파일을 선택한 뒤 어떤 파일이 등록될지 확인하기 어려웠습니다.
- 업로드 후 분석을 다시 실행해야 하는 것처럼 보여 흐름이 끊겼습니다.

수정:

- PDF 업로드를 직접 입력보다 먼저 표시합니다.
- PrimeVue FileUpload를 적용했습니다.
- 선택한 파일명과 파일 크기를 표시합니다.
- 제목이 비어 있으면 PDF 파일명으로 자동 입력합니다.
- 버튼 문구를 `PDF 업로드 및 분석`으로 변경했습니다.
- 업로드 직후 분석을 자동으로 시작하고 문서 상세로 이동합니다.
- 처리 중에는 중복 클릭을 막고 로딩 상태를 표시합니다.

## 4. 불명확한 요구사항 검토

### 4.1 불명확한 요구사항이 눈에 띄지 않던 문제

문제:

- 정상 요구사항과 불명확한 요구사항이 같은 목록에 같은 형태로 표시됐습니다.
- 모든 행의 액션이 동일해 무엇을 먼저 검토해야 하는지 알기 어려웠습니다.
- 검토가 필요한 항목을 찾으려면 전체 목록을 하나씩 열어봐야 했습니다.

수정:

- `불명확성 발견`, `보완 답변 필요` 상태를 목록 최상단에 배치합니다.
- 불명확한 항목의 액션은 `불명확성 확인`으로 표시합니다.
- 그 외 항목은 `요구사항 보기`로 표시합니다.
- 요구사항 코드와 제목을 본문에서 분리해 빠르게 훑을 수 있게 했습니다.
- 번호, 본문과 액션 위치를 행마다 동일하게 맞췄습니다.
- 여러 불명확 항목이 있으면 각 항목을 직접 선택할 수 있습니다.
- 불명확 항목 왼쪽의 빨간 선은 제거하고, 항목 구분과 액션 문구로 상태를 전달합니다.
- 여러 항목 중 대상을 설명하지 못하던 `검토 필요 바로 보기`는 제거했습니다.

번호 처리:

- 불명확 항목을 위로 올려도 원문에서 추출된 `sequenceNo`는 유지합니다.
- 따라서 5번 요구사항이 1번보다 먼저 보일 수 있지만 요구사항 누락은 아닙니다.

### 4.2 상태 명칭 변경

- `명확도 여정` → `처리 단계`
- `EXTRACTED` → `추출 완료`
- `AMBIGUOUS` → `불명확성 발견`
- `CLARIFYING` → `보완 답변 필요`
- `IN_REVIEW` → `수정안 승인 대기`
- `CONFIRMED` → `확정 완료`
- `분석 중`은 실제 AI 비동기 작업이 실행 중일 때만 사용합니다.

## 5. 결과 화면

### 5.1 미리보기 용어와 배치 정리

문제:

- `문서 보기`, `문서 열기`, `Preview`는 고객 질문서와 개발팀 결과라는 실제 목적을 설명하지 못했습니다.
- 개발팀용 미확정 요구사항에서 상태와 버전이 각각 떨어져 배치되어 `추출 완료` 상태가 카드 중앙에 홀로 표시됐습니다.

수정:

- 화면 제목은 `문서 미리보기`로 표시합니다.
- 결과 구분은 `고객 질문서`, `개발팀용`으로 표시합니다.
- 미확정 요구사항의 상태와 버전을 오른쪽 정보 묶음으로 정렬했습니다.
- 원문, 질문과 답변의 글자 크기를 본문 수준으로 올렸습니다.

## 6. 아직 필요한 백엔드 기능

문제:

- 불명확성이 없는 요구사항은 추가 답변 없이 바로 확정할 수 있어야 하지만 현재 직접 승인 API가 없습니다.

프론트 처리 기준:

- 프론트에서 임의로 확정 상태를 만들지 않습니다.
- 백엔드 API가 제공되면 열린 문제가 없는 `추출 완료` 요구사항에 `바로 승인`을 연결합니다.
- 승인 완료 후 요구사항 목록과 개발팀용 결과를 다시 조회합니다.
- 상세 계약은 [불명확성 없는 요구사항 직접 승인 기능 요청서](백엔드-추가-수정요청사항.md)를 따릅니다.

## 7. 검증 체크리스트

- [ ] 영문 화면명과 개발용 문구가 노출되지 않는다.
- [ ] 브라우저 탭과 상단바에 투명 배경 ReqBridge 심볼이 표시된다.
- [ ] 프로젝트와 문서를 내부 ID가 아닌 이름으로 구분할 수 있다.
- [ ] 직접 입력 필드가 빈 값으로 시작한다.
- [ ] PDF 업로드가 직접 입력보다 먼저 보인다.
- [ ] 선택한 PDF의 파일명과 크기를 확인할 수 있다.
- [ ] 한 번의 액션으로 PDF 업로드와 분석이 이어진다.
- [ ] 불명확한 요구사항을 목록에서 바로 찾을 수 있다.
- [ ] 불명확 요구사항이 여러 개여도 각각 선택할 수 있다.
- [ ] 상태 문구만 보고 분석 중, 답변 필요와 승인 대기를 구분할 수 있다.
- [ ] 질문, 문제, 작업과 수정안의 내부 ID가 주요 정보로 노출되지 않는다.
- [ ] 고객 질문서와 개발팀용 결과의 목적을 이름만 보고 구분할 수 있다.
- [ ] 개발팀용 미확정 요구사항의 상태와 버전이 오른쪽에 함께 정렬된다.
