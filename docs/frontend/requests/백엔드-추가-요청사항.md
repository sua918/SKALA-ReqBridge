# 불명확성 없는 요구사항 직접 승인 기능 요청

## 1. 배경

문서 분석 결과 불명확성이 발견된 요구사항은 다음 흐름으로 확정할 수 있습니다.

`보완 답변 필요 → 질문 답변 → 수정안 생성 → 수정안 승인 → 확정 완료`

반면 불명확성이 없는 요구사항은 `EXTRACTED` 상태에 머물며 승인할 수 없습니다. 현재 도메인은 `CONFIRMED` 전환 시 승인된 수정안을 필수로 요구하고, 공개 API에는 요구사항 원문을 바로 승인하는 경로가 없습니다.

사용자는 불명확성이 없는 요구사항을 원문 그대로 승인할 수 있어야 합니다. 감사 이력과 기존 데이터 제약을 유지하기 위해, 직접 승인 시 원문을 기준 리비전으로 생성하고 같은 트랜잭션에서 승인·확정합니다.

## 2. 목표 흐름

### 불명확성 없음

`추출 완료 → 바로 승인 → 확정 완료`

### 불명확성 있음

기존 흐름을 유지합니다.

`불명확성 발견 → 보완 답변 필요 → 수정안 승인 대기 → 확정 완료`

## 3. API 제안

### 요청

`POST /api/requirements/{requirementId}/confirm`

```json
{
  "expectedContentVersion": 1
}
```

- 미정의 필드는 기존 API 정책과 동일하게 거부합니다.
- `expectedContentVersion`은 JSON-safe 양의 정수여야 합니다.

### 성공 응답

`200 OK`

```json
{
  "data": {
    "requirement": {
      "id": 1,
      "status": "CONFIRMED",
      "contentVersion": 1,
      "approvedRevisionId": 10,
      "confirmedText": "원문 요구사항"
    },
    "revision": {
      "id": 10,
      "requirementId": 1,
      "revisionNo": 1,
      "text": "원문 요구사항",
      "source": "MANUAL",
      "status": "APPROVED",
      "basedOnClarificationIds": []
    }
  }
}
```

응답 필드 명칭과 공통 envelope는 기존 revision review 응답 형식에 맞춰 조정할 수 있습니다.

## 4. 승인 가능 조건

다음 조건을 모두 만족할 때만 직접 승인합니다.

- 요구사항이 존재합니다.
- 현재 상태가 `EXTRACTED`입니다.
- `expectedContentVersion`이 현재 버전과 일치합니다.
- 연결된 `OPEN` ambiguity issue가 없습니다.
- 연결된 `WAITING` clarification이 없습니다.
- 해당 요구사항에 `PENDING` 또는 `PROCESSING` 분석 작업이 없습니다.
- `PROPOSED` 수정안이 없습니다.
- 기존 승인 수정안과 확정 본문이 없습니다.

`AMBIGUOUS`, `CLARIFYING`, `IN_REVIEW` 요구사항은 직접 승인할 수 없습니다. 기존 질문·수정안 검토 흐름을 사용해야 합니다.

## 5. 트랜잭션 처리

하나의 트랜잭션에서 다음을 수행합니다.

1. 요구사항 행을 비관적 잠금으로 조회합니다.
2. 버전과 승인 가능 조건을 검증합니다.
3. `originalText`와 동일한 본문으로 기준 리비전을 생성합니다.
4. 리비전 source는 `MANUAL`, 근거 clarification 목록은 빈 배열로 저장합니다.
5. 요구사항 상태를 `IN_REVIEW`로 전환합니다.
6. 생성한 리비전을 `APPROVED`로 전환합니다.
7. 생성한 리비전 ID와 본문으로 요구사항을 `CONFIRMED` 처리합니다.
8. 어느 단계든 실패하면 리비전과 요구사항 변경을 모두 롤백합니다.

기존 `requirement` 테이블의 확정 제약과 `approved_revision_id` 외래 키를 유지합니다. 승인 이력 없이 `CONFIRMED`만 직접 기록하거나 제약을 완화하지 않습니다.

## 6. 오류 응답

| 상황 | HTTP | 코드 | 메시지 의미 |
|---|---:|---|---|
| 요구사항 없음 | 404 | 기존 NOT_FOUND 코드 | 요구사항을 찾을 수 없음 |
| 버전 불일치 | 409 | `CONTENT_VERSION_CONFLICT` | 최신 상태 재조회 필요 |
| 열린 불명확성 존재 | 409 | `OPEN_ISSUES_REMAIN` | 보완 질문 흐름 필요 |
| 승인 가능한 상태 아님 | 409 | `REQUIREMENT_NOT_DIRECTLY_CONFIRMABLE` | 현재 상태에서는 직접 승인 불가 |
| 분석 작업 진행 중 | 409 | `ANALYSIS_IN_PROGRESS` | 진행 작업 완료 후 재시도 |
| 이미 확정됨 | 200 또는 409 | 아래 멱등성 정책 참고 | 중복 요청 처리 |

## 7. 멱등성과 동시성

- 같은 요구사항에 대한 중복 클릭이 리비전을 두 개 만들면 안 됩니다.
- 권장 정책은 이미 직접 승인된 요구사항에 동일 요청이 다시 오면 기존 requirement와 approved revision을 `200 OK`로 반환하는 것입니다.
- 이미 다른 수정안 승인 경로로 확정된 요구사항이면 기존 확정 결과를 반환하되 새 리비전을 만들지 않습니다.
- 동시에 두 요청이 들어와도 잠금 이후 한 요청만 리비전을 생성해야 합니다.
- `uq_revision_requirement_number`, `uq_revision_single_proposed` 제약 위반은 내부 오류가 아니라 일관된 409 또는 멱등 성공으로 처리합니다.

## 8. 개발팀용 미리보기 영향

직접 승인된 요구사항도 기존 개발팀용 preview의 `confirmedRequirements`에 포함되어야 합니다.

- `approvedRevision.text`: 원문과 동일
- `approvedRevision.status`: `APPROVED`
- `evidenceAnswers`: 빈 배열
- 고객 질문서에는 표시되지 않음
- 미확정 요구사항 목록에서는 제거됨

## 9. 테스트 요구사항

### 서비스 테스트

- `EXTRACTED`이며 이슈가 없는 요구사항 직접 승인 성공
- 원문과 동일한 승인 리비전 생성
- requirement와 revision이 같은 트랜잭션에서 확정
- 열린 이슈가 있으면 거부
- 답변 대기 질문이 있으면 거부
- `CLARIFYING` 및 `IN_REVIEW` 상태에서 거부
- 분석 진행 중 거부
- content version 불일치 거부
- 중복 요청 시 리비전 중복 생성 방지
- 동시 요청 시 하나의 승인 리비전만 생성
- 저장 실패 시 전체 롤백

### API 테스트

- 정상 요청 `200`
- 미정의 JSON 필드 `400`
- 숫자 범위·형식 오류 `400`
- 도메인 충돌별 오류 코드와 `409`
- 확정 requirement와 approved revision 응답 형식 검증

### Preview 회귀 테스트

- 직접 승인 전에는 `unconfirmedRequirements`에 포함
- 직접 승인 후에는 `confirmedRequirements`에 포함
- 직접 승인된 항목의 `evidenceAnswers`는 빈 배열
- 기존 질문 답변 후 수정안 승인 흐름은 영향 없음

## 10. 프론트 연동 계약

백엔드 API 제공 후 프론트는 다음 조건에서만 `바로 승인` 버튼을 표시합니다.

- status가 `EXTRACTED`
- 열린 문제 수가 0
- 활성 분석 작업이 없음

클릭 시 현재 `contentVersion`을 그대로 전송합니다. 성공 후 요구사항 목록, 상세, 개발팀용 preview를 다시 조회합니다. 409 버전 충돌 시 최신 상태를 불러오고 사용자에게 재확인을 요청합니다.
